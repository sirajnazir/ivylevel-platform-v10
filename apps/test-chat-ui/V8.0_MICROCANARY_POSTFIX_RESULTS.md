## Summary of Fixes Applied

### 1. Hash Function (llmAdapter.ts)
**Issue:** Simple string hash caused bias in cohort assignment (43% vs 30% target)

**Fix:**
```typescript
// Before: Simple string hash with collision bias
function simpleHash(str: string): number {
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    const char = str.charCodeAt(i);
    hash = ((hash << 5) - hash) + char;
    hash = hash & hash;
  }
  return Math.abs(hash);
}

// After: SHA256-based deterministic hash
function simpleHash(str: string): number {
  const hash = crypto.createHash("sha256").update(str).digest("hex");
  return parseInt(hash.slice(0, 6), 16) % 100;
}
```

**Result:** ✅ Adapter share: 26.6% (within 25-35% target)

## Appendix: Technical Notes

### Why Tone Scores Are Low
The tone guard architecture scores responses BEFORE adding warmth prefix:

```typescript
export async function guardAndPolish(text: string, intent: string): Promise<GuardResult> {
  const toneScore = score(text, TONE_RGX);  // ← Scores raw LLM output
  // ...
  if (toneScore < 0.10) {
    out = `I'm with you. ${text}`;  // ← Adds warmth AFTER scoring
    rewritten = true;
  }
  return { text: out, toneScore, proofScore, rewritten };
}
```

**This is correct behavior:**
- Measures raw model warmth (adapter vs base comparison)
- Guard ensures all responses have minimum warmth
- User sees warm response regardless of model

**To measure final response warmth:**
Would need to score AFTER guard processing, but that defeats the purpose of measuring adapter improvement.

### SHA256 Hash Distribution
The new hash function provides better distribution:

```typescript

```

Result: 30 requests → 8 in adapter range (0-29), 22 in base range (30-99) = 26.7%
