## HOW WE'RE DOING IT (Strategy)

### Core Principle: INCREMENTAL ENHANCEMENT

**❌ NOT a rebuild:** We keep all working v3.1 components

**✅ Incremental waves:** Each wave adds new capabilities without breaking existing features

**✅ Feature-flagged:** All changes behind flags, can disable instantly

**✅ Parallel development:** v3.1 stays in production while we build v3.2

### Clean Architecture (First Principles)

**Before v3.1:** Mixed abstractions, unclear boundaries
```
resolverTools.ts  // What kind of tools? SQL? API?
compose.ts        // Composes what? How?
humanizer.ts      // Humanizes what? When?
```

**After v3.2:** Clear, intention-revealing names
```
knowledge/facts-plane.ts       // SQL-only, deterministic facts
knowledge/narrative-plane.ts   // RAG-only, soft matches
evidence/chip-creator.ts       // Creates provenance chips
cognition/tool-bus.ts          // Central tool execution
cognition/policy-gate.ts       // Access control + budgets
cognition/eq-adapter.ts        // Emotional tone adaptation
```

### Risk Mitigation

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Breaking existing agents | Medium | High | Feature flags, parallel dev, comprehensive tests |
| Performance regression | Low | Medium | Benchmark each wave, optimize before merge |
| Database migration issues | Low | Medium | Dry runs, backups, rollback scripts |
| Timeline overrun | Medium | Medium | Buffer time (16 weeks → 20 weeks max), weekly check-ins |

**Overall Risk:** 🟡 **MEDIUM** (manageable with mitigation)

## WAVE 1 DEEP DIVE (First 2 Weeks)

### Goal: Evidence Chips + Temporal UDFs (Foundation)

**Priority:** 🔴 P0 (Blocks all other waves)

### What We're Building

**1. Evidence Chips System**
- Universal provenance tracking for all data sources
- 4 chip types: SQL (facts), Narrative (RAG), Artifact (files), EQ (tone)
- Database table: `chips` with trace_id for debugging
- Every resolver call creates a chip

**2. Temporal SQL UDFs**
- Canonical functions: `award_nth()`, `gpa_as_of()`, `deadline_latest()`, etc.
- Replaces scattered ad-hoc date logic across resolvers
- Deterministic, cacheable, consistent

**3. 412 Error Handling**
- Missing evidence returns HTTP 412 "Evidence Missing"
- Friendly user message: "No awards found. Please add award information to continue."
- Never hallucinate when data is missing

### Database Changes (Wave 1)

```sql
-- Chips table
CREATE TABLE chips (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  kind text CHECK (kind IN ('sql', 'narrative', 'artifact', 'eq')),
  source jsonb NOT NULL,
  hash text,
  trace_id text NOT NULL,
  student_id text NOT NULL,
  created_at timestamptz DEFAULT now()
);

-- Temporal UDFs
CREATE FUNCTION award_nth(student_id, n, as_of) RETURNS TABLE(...);
CREATE FUNCTION gpa_as_of(student_id, as_of) RETURNS numeric;
CREATE FUNCTION deadline_latest(student_id, category, as_of) RETURNS date;
-- ... etc
```

### Code Changes (Wave 1)

**New Files:**
- `src/evidence/chip-creator.ts` - Chip creation logic
- `src/errors/evidence-errors.ts` - Error412 class
- `migrations/001_evidence_chips.sql` - Database schema
- `migrations/002_temporal_udfs.sql` - SQL functions

**Modified Files:**
- `src/tools/resolverTools.ts` - Add chip creation to all 19 tools
- `src/resolvers/*.ts` - Use temporal UDFs instead of ad-hoc queries

### Acceptance Criteria (Wave 1)

- ✅ 100% fact-based responses include ≥1 SQL chip
- ✅ Missing data returns 412 errors with helpful messages
- ✅ All temporal logic uses canonical UDFs (no ad-hoc date filtering)
- ✅ Unit tests pass (≥80% coverage)
- ✅ No breaking changes to existing agents
