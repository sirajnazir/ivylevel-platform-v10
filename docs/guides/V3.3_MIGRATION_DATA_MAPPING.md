# v14 → v3.2 Migration Data Mapping & Verification

**Version:** v3.3.0
**Date:** 2025-10-24
**Student:** huda-2025
**Purpose:** Complete traceability of all data migrated from v14 to v3.2, ensuring zero data loss

---

## Executive Summary

**Migration Result:** ✅ **100% DATA PRESERVED**

- **v14 Source Data:** 258 fact observations + 7 courses + 2 GPA records + 28 colleges + 3 canon docs + 185 KB intel files
- **v3.2 Target Data:** 97 evidence chips (5 SQL + 2 RAG + 89 EQ + 1 NARRATIVE)
- **Data Loss:** **ZERO** - All v14 data preserved in original tables + transformed to v3.2 format
- **Architecture:** v3.2 is a **superset** of v14 (130 total tables, includes all v14 tables)

---

## Migration Philosophy

### v3.2 = Enhanced v14, Not Replacement

1. **Additive Transformation:** v14 tables remain intact, v3.2 adds new `chips` table
2. **Dual Format:** Data exists in BOTH v14 format (original) AND v3.2 format (chips)
3. **Backward Compatibility:** All v14 queries still work
4. **Forward Enhancement:** v3.2 UI consumes chips for richer UX

### Why This Approach?

- **Rationale:** v14 had rich temporal data that shouldn't be lost during migration
- **Strategy:** Transform v14 data into v3.2 Evidence Chips while preserving source
- **Benefit:** Can always regenerate chips from v14 data if needed
- **Risk Mitigation:** Migration is reversible (can delete chips, v14 data intact)

| `course_name` | `course_title` | Matches actual v14 schema (academic_courses.course_title) |
| `observation_date` | `event_date` | Matches actual v14 schema (fact_observations.event_date) |
| `value` | `value_numeric` + `value_text` | v14 has separate fields for numeric vs text |
| `metadata` | `meta` | Matches actual v14 schema (fact_observations.meta) |
| `category` | `bucket_category` | Matches actual v14 schema (college_list.bucket_category) |
| `document_type` | `source_type` | Matches actual v14 schema (canon.source_type) |
| `content` | N/A | Canon table never had content (only drive_link pointers) |

## Enhancement Rationale: Why v3.2 is "Enhanced v14"

### 1. Unified Evidence Model

**v14 Problem:** Data scattered across 130+ tables
- GPA in academic_gpa
- Courses in academic_courses
- Test scores in fact_observations
- Colleges in college_list
- Coaching in KB files (file system)

**v3.2 Solution:** Single `chips` table with semantic types
- All evidence in one place
- Queryable by `kind` (SQL, RAG, EQ, LLM, NARRATIVE)
- UI can fetch all evidence with one query: `SELECT * FROM chips WHERE student_id = 'huda-2025'`

### 2. Provenance Tracking

**v14 Limitation:** No audit trail for how data was created
- Can't tell if GPA was manual entry vs imported
- Can't trace which coaching session generated insight

**v3.2 Enhancement:**
- `trace_id`: "migration_v14_to_v32_gpa" → clear provenance
- `source.metadata.migration_source`: "v14_to_v32"
- `hash`: Deduplication (prevent same data from being migrated twice)
- `created_at`: When chip was created (audit log)

### 3. Temporal Aggregation

**v14 Structure:** Individual records (one row per observation)
- 16 ACT scores = 16 rows in fact_observations
- Hard for UI to show "ACT progression timeline"

**v3.2 Structure:** Aggregated arrays
- 16 ACT scores = 1 chip with 16-element `source.result` array
- UI can render line chart with single chip
- Maintains all granularity (nothing lost)

### 4. Semantic Typing

**v14 Limitation:** Everything is a `fact_observation`
- SAT score and award both use same table
- Query needs `WHERE kind = 'sat_total_score'`

**v3.2 Enhancement:**
- Test scores → SQL chip (fact-based)
- Awards → RAG chip (retrieved achievements)
- Coaching insights → EQ chip (emotional growth)
- Canon docs → NARRATIVE chip (longitudinal story)

**Benefit:** UI can render different chip types with appropriate UX (charts for SQL, timeline for EQ, etc.)

### 5. LLM-Ready Format

**v14 Limitation:** Relational data hard for LLMs to consume
- Need to write SQL to extract context
- Multi-table JOINs required

**v3.2 Enhancement:**
- RAG chips have `rag_query` field: "What colleges is Huda considering?"
- EQ chips have `coaching_insight` field: Natural language content
- LLMs can consume chips directly as JSON context
- Enables RAG workflows: retrieve relevant chips → pass to LLM
