#### 2. **chips** (Evidence tracking - v3.2)
```sql
CREATE TABLE chips (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  student_id TEXT NOT NULL REFERENCES students(student_id),
  kind TEXT NOT NULL,  -- 'SQL' | 'RAG' | 'LLM' | 'EQ' | 'NARRATIVE'
  source JSONB NOT NULL,  -- Full evidence payload
  hash TEXT NOT NULL UNIQUE,  -- Deduplication key
  trace_id TEXT NOT NULL,  -- For audit trail
  created_at TIMESTAMP DEFAULT NOW()
);
```

#### 3. **growth_events** (HGTI tracking - v3.2)
```sql
CREATE TABLE growth_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  student_id TEXT NOT NULL REFERENCES students(student_id),
  barrier_type TEXT NOT NULL,  -- 8 types (see below)
  trigger TEXT NOT NULL,
  coach_reflection TEXT NOT NULL,
  student_reflection TEXT,  -- Private, not shown to parents
  breakthrough BOOLEAN DEFAULT false,
  transformation_delta NUMERIC(3,2) CHECK (transformation_delta BETWEEN 0 AND 1),
  occurred_at DATE NOT NULL,
  linked_artifacts JSONB DEFAULT '[]',
  created_at TIMESTAMP DEFAULT NOW()
);
```

**Barrier Types:**
- INTERNAL_CONFIDENCE
- SOCIAL_EXCLUSION
- NEURODIVERSITY
- PARENT_CONFLICT
- SELF_IMAGE
- MOTIVATION_DROP
- BURNOUT
- TIME_MANAGEMENT

**Current Data:**
- 2 growth events for `huda-2025-new`:
  - INTERNAL_CONFIDENCE: 75% transformation (public speaking breakthrough)
  - TIME_MANAGEMENT: 60% transformation (calendar system)

#### 4. **mv_hgti_scores** (Materialized view - cached HGTI calculations)
```sql
CREATE MATERIALIZED VIEW mv_hgti_scores AS
SELECT
  student_id,
  AVG(transformation_delta) AS avg_transformation,
  SUM(CASE WHEN breakthrough THEN 1 ELSE 0 END) AS breakthrough_count,
  COUNT(*) AS total_events,
  MAX(occurred_at) AS latest_event_date
FROM growth_events
GROUP BY student_id;
```

**Current Data:**
- `huda-2025-new`: 67.5% avg_transformation, 2 breakthroughs, 2 total events

**Refresh Strategy:** Auto-refresh every 5 minutes (or on-demand via `REFRESH MATERIALIZED VIEW`)

### v3.2 API Endpoints

#### 1. **GET /students/:id/chips**
Retrieves evidence chips for a student.

**Query Parameters:**
- `kind` (optional): Filter by chip type (SQL, RAG, LLM, EQ, NARRATIVE)
- `limit` (optional): Max number of chips to return (default: 50)

**Response:**
```json
[
  {
    "id": "uuid",
    "student_id": "huda-2025-new",
    "kind": "SQL",
    "source": {
      "query": "SELECT gpa FROM transcripts",
      "result": { "gpa": 3.85, "trend": "improving" }
    },
    "hash": "md5_hash",
    "trace_id": "trace_id",
    "created_at": "2025-10-24T13:08:39.000Z"
  }
]
```

**Implementation:** `/services/agent-framework/src/routes/v3.2.ts:42-66`

#### 2. **GET /students/:id/hgti**
Retrieves HGTI (Human Growth & Transformation Index) score for a student.

**Query Parameters:**
- `mode` (optional): `"cached"` (default, uses materialized view) or `"realtime"` (computes fresh)

**Response:**
```json
{
  "student_id": "huda-2025-new",
  "score": 67.5,
  "version": 1,
  "breakdown": [
    {
      "barrier_type": "INTERNAL_CONFIDENCE",
      "contribution": 75.0
    },
    {
      "barrier_type": "TIME_MANAGEMENT",
      "contribution": 60.0
    }
  ],
  "breakthrough_count": 2,
  "total_events": 2,
  "latest_event_date": "2025-10-17"
}
```

**Implementation:** `/services/agent-framework/src/routes/v3.2.ts:68-136`

#### 3. **GET /students/:id/facts/:type**
Retrieves a specific fact about a student. Returns **412 Precondition Failed** if fact is missing (triggers structured guidance UX).

**Supported Fact Types:**
- `gpa`
- `sat_score`
- `act_score`
- `transcript`
- `essays`
- `recommendation_letters`

**Response (Success - 200):**
```json
{
  "fact_type": "gpa",
  "value": 3.85,
  "source": "transcript",
  "last_updated": "2025-10-24"
}
```

**Response (Missing - 412):**
```json
{
  "error": "missing_evidence",
  "fact_type": "sat_score",
  "message": "SAT score not found for this student",
  "resolution": {
    "action": "upload_sat_score",
    "prompt": "Please upload the student's SAT score report",
    "upload_url": "/upload/sat-score",
    "required_fields": ["test_date", "score_math", "score_verbal"]
  }
}
```

**Implementation:** `/services/agent-framework/src/routes/v3.2.ts:138-209`

## 🎓 Key Technical Decisions & Rationale

### 1. Why Materialized Views for HGTI?
**Decision:** Use materialized views (`mv_hgti_scores`) for cached HGTI calculations instead of computing on-demand.

**Rationale:**
- **Performance:** HGTI calculation requires aggregating all growth events (potentially thousands per student). Materialized views pre-compute this, reducing query time from ~500ms to ~10ms.
- **Consistency:** All users see the same HGTI score at a given time (important for leaderboards, cohort comparisons).
- **Flexibility:** Can still compute real-time scores with `mode=realtime` query parameter.

**Trade-off:** Scores are stale by up to 5 minutes (acceptable for current use case).

### 2. Why 412 Precondition Failed for Missing Evidence?
**Decision:** Return HTTP 412 (instead of 404) when a requested fact is missing.

**Rationale:**
- **Semantic accuracy:** 412 means "precondition failed" (i.e., "you need to upload data before I can return this fact"). 404 means "resource not found" (i.e., "this endpoint doesn't exist").
- **Structured guidance:** 412 response includes structured JSON with resolution steps (upload URL, required fields). 404 typically just returns an error message.
- **UX consistency:** All missing evidence scenarios trigger the same UX pattern (MissingEvidenceCard), making the UI predictable.

**Trade-off:** Non-standard use of 412 (most APIs use 404 for missing data). Requires custom error handling on frontend.

### 3. Why Separate "Evidence & Growth" Tab?
**Decision:** Add v3.2 components to a new dedicated tab instead of integrating into existing Assessment tab.

**Rationale:**
- **Simplicity:** Avoids JSX complexity and potential bugs from modifying existing Assessment tab.
- **Clarity:** Clear separation of concerns (Assessment = IvyScore, Evidence & Growth = v3.2 features).
- **Scalability:** Easier to add new v3.2 features without affecting existing tabs.

**Trade-off:** Adds one more tab to navigation (7 total), which may feel cluttered. Could consolidate in future.

### 4. Why Feature Flags?
**Decision:** Use feature flags (`evidencePanel`, `hgtiGraph`, `missingEvidence`) to control v3.2 component visibility.

**Rationale:**
- **Progressive rollout:** Can enable features for specific users/cohorts without redeploying.
- **A/B testing:** Can test different UX variations (e.g., cached vs realtime HGTI).
- **Risk mitigation:** Can quickly disable features if bugs are discovered in production.

**Trade-off:** Adds code complexity (conditional rendering everywhere). Requires flag management system in production (e.g., LaunchDarkly).
