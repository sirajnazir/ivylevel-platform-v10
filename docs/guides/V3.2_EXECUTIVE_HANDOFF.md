## 🔑 KEY TECHNICAL DECISIONS

### 1. Additive Architecture (Zero Breaking Changes)

**Decision:** All v3.2 features added without modifying existing v14 → v2.1 code.

**Rationale:**
- Preserves battle-tested functionality
- Enables gradual rollout
- Reduces regression risk

**Implementation:**
- CREATE TABLE IF NOT EXISTS (no schema changes to existing tables)
- New TypeScript modules (no modifications to existing resolvers)
- Feature flags for gradual enablement (IVYSCORE_VERSION, ENABLE_MV_REFRESHER, etc.)

---

### 2. Database-Level Security (RLS vs Application-Level)

**Decision:** Use PostgreSQL Row-Level Security (RLS) instead of application-level filtering.

**Rationale:**
- Defense in depth (security enforced at DB layer)
- Prevents accidental data leaks (even if WHERE clause forgotten)
- Industry standard for multi-tenant systems

**Implementation:**
- RLS policies on 4 tables (chips, growth_events, agent_runs, system_events)
- Session-scoped variables (app.student_id, app.coach_id)
- LOCAL scope for automatic cleanup

**Trade-offs:**
- ✅ Pro: Zero-trust security (DB enforces isolation)
- ✅ Pro: No code changes needed in queries
- ⚠️ Con: Requires RLS-aware connection helpers
- ⚠️ Con: Performance overhead (minimal in practice)

---

### 3. Exactly-Once Delivery (Outbox Pattern + Redis)

**Decision:** Use outbox pattern with Redis idempotency instead of at-least-once delivery.

**Rationale:**
- Prevents duplicate events (critical for billing, notifications)
- Industry standard for distributed systems
- Redis provides fast idempotency checks (< 1ms)

**Implementation:**
- Outbox table (database transactions)
- Background processor (polls every 5s)
- Redis deduplication (1-hour TTL)

**Trade-offs:**
- ✅ Pro: Guaranteed no duplicates
- ✅ Pro: Survives crashes (outbox persisted in DB)
- ⚠️ Con: Adds Redis dependency
- ⚠️ Con: Eventual consistency (max 5s delay)

---

### 4. Materialized Views (CONCURRENTLY vs Realtime)

**Decision:** Use materialized views with CONCURRENTLY refresh instead of realtime computation.

**Rationale:**
- HGTI score computation expensive (AVG over all growth_events)
- Most queries can tolerate 5-min staleness
- CONCURRENTLY refresh = zero downtime

**Implementation:**
- Materialized view: mv_hgti_scores
- Cron refresh every 5 minutes (CONCURRENTLY)
- Realtime fallback available (opts.realtime = true)

**Trade-offs:**
- ✅ Pro: Fast queries (pre-computed)
- ✅ Pro: Zero downtime during refresh
- ⚠️ Con: Max 5-min stale data
- ⚠️ Con: Requires background worker

---

### 5. Phased HGTI Rollout (Feature Flags)

**Decision:** Use IVYSCORE_VERSION env var (1-4) instead of immediate 28% weight.

**Rationale:**
- Allows A/B testing (compare v1 vs v4)
- Gradual impact on student scores
- Easy rollback if issues detected

**Implementation:**
- v1: 0% HGTI (baseline)
- v2: 10% HGTI
- v3: 20% HGTI
- v4: 28% HGTI (target)

**Trade-offs:**
- ✅ Pro: Safe gradual rollout
- ✅ Pro: A/B testable
- ⚠️ Con: Requires version tracking in ivyscore_history

---

### 6. PII Scrubbing (Redaction vs Encryption)

**Decision:** Redact PII before persistence instead of encrypting.

**Rationale:**
- Evidence chips used for debugging/audit (no need to recover PII)
- Simpler compliance (GDPR "right to be forgotten")
- No key management overhead

**Implementation:**
- Regex patterns for: email, phone, SSN, DOB, address, zipcode
- Secret key detection (API_KEY, TOKEN, PASSWORD in param names)
- SHA-256 hashing for deduplication (same query = same hash)

**Trade-offs:**
- ✅ Pro: Simple compliance (no PII stored = no breach risk)
- ✅ Pro: No key management
- ⚠️ Con: Cannot recover original PII (acceptable for audit use case)

## ⚠️ RISKS & MITIGATIONS

### Risk 1: RLS Performance Overhead

**Risk:** RLS policies add query overhead (est. 5-10%)

**Mitigation:**
- Use indexes on student_id (already exists)
- Monitor query performance in staging
- Consider caching for high-frequency queries

**Contingency:**
- Disable RLS on low-risk tables (system_events)
- Use materialized views for heavy aggregations

---

### Risk 2: Redis Dependency (Outbox Processor)

**Risk:** Redis unavailable → outbox processor fails

**Mitigation:**
- Redis runs in HA mode (cluster)
- Graceful degradation: processor retries on Redis failure
- Outbox persisted in DB (no data loss)

**Contingency:**
- Fall back to at-least-once delivery (accept duplicates temporarily)
- Alert on Redis downtime (PagerDuty)

---

### Risk 3: HGTI Adoption (Low Usage)

**Risk:** Coaches don't record growth events → HGTI underutilized

**Mitigation:**
- In-app prompts for coaches (after breakthroughs)
- Training materials on HGTI value
- Show growth timeline in student dashboard

**Contingency:**
- Keep HGTI at 0% (v1) until adoption improves
- Backfill growth events from conversation transcripts (NLP)

---

### Risk 4: Migration Failures (Staging/Production)

**Risk:** Migration 007 fails due to missing dependencies (kb_items, students)

**Mitigation:**
- Run migrations in order: 000 → 01 → 007
- Verify tables exist before migration 007
- Create rollback scripts for each migration

**Contingency:**
- Database backup before migration (pg_dump)
- Rollback procedure documented in deployment checklist
