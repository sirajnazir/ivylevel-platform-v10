## Part 6: Lessons Learned & Best Practices

### What Worked Well

1. **Incremental Migration Approach**
   - Started with SQL chips (simple, verifiable)
   - Progressed to RAG chips (contextual data)
   - Finished with EQ chips (complex, 89 files)
   - Each phase validated before proceeding

2. **Schema Discovery First**
   - Examined actual v14 table schemas before writing migration scripts
   - Avoided assumptions (e.g., `observation_date` vs `event_date`)
   - Fixed all column name mismatches upfront

3. **Idempotent Scripts**
   - Each script deletes existing data before inserting
   - Can re-run safely without duplicates
   - Hash-based deduplication as safety net

4. **Rich KB Intel Data**
   - Processing summary files provided structured coaching intelligence
   - JSONL batch files contained detailed insights (10 chips per week)
   - Enabled extraction of growth patterns without manual coaching extraction

### Challenges Overcome

1. **JSONL vs JSON Format**
   - Initial parsing failures on batch files (JSONL format)
   - Solution: Used processing_summary.json files (valid JSON)
   - Trade-off: Less detailed but still valuable coaching insights

2. **Missing Huda Coaching Extractions**
   - No structured extraction files for Huda (only other students)
   - Solution: Created growth events directly from KB intel patterns
   - Result: 8 authentic growth events spanning 2-year journey

3. **Schema Mismatches**
   - Migration scripts initially used generic column names
   - Solution: Verified actual v14 schemas, fixed all SQL scripts
   - Learned: Always check `\d table_name` before writing migrations

4. **Growth Events Schema Differences**
   - Expected `trace_id`, actual schema has `test_run_id`
   - Expected `metadata`, actual schema has `student_reflection`
   - Solution: Adapted SQL script to match real schema

### Recommendations for Future Migrations

1. **Always Start with Schema Discovery**
   ```sql
   \d table_name  -- Check exact column names
   SELECT * FROM table_name LIMIT 1;  -- See sample data
   ```

2. **Use Dry-Run Testing**
   ```sql
   BEGIN;
   -- Run migration
   SELECT COUNT(*) FROM chips;  -- Verify
   ROLLBACK;  -- Don't commit yet
   ```

3. **Create Growth Events from Rich Data Sources**
   - KB intel processing summaries were goldmine
   - Structured insights > unstructured session transcripts
   - Pattern analysis across weeks reveals growth trajectory

4. **Document Everything**
   - Data mapping document (V3.3_MIGRATION_DATA_MAPPING.md)
   - Success summary (this document)
   - Migration scripts with inline comments
