```
    ↓
```

- ❌ Scattered logic across 6+ files

### Proposed v3.0: Clean Layered Flow

```
HTTP Request
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 1: PERCEPTION                                            │
│  MessageParser → StudentContextExtractor → SessionStateDetector│
│  Output: PerceptionOutput (who, what, when, context)           │
└─────────────────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 2: KNOWLEDGE                                             │
│  StudentFactsRetriever + CoachingIntelligenceRetriever +       │
│  TemporalContextResolver                                       │
│  Output: KnowledgeOutput (facts + coaching intel + temporal)   │
└─────────────────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 3: COGNITION                                             │
│  IntentRouter → AgentSelector → DecisionMaker                  │
│  Output: AgentDecision (what to say, confidence, reasoning)    │
└─────────────────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 4: ACTION                                                │
│  ResponseExecutor + StateUpdater + EventEmitter                │
│  Output: ExecutionResult (delivered response + state updates)  │
└─────────────────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 5: INTERFACE                                             │
│  ViewRenderer (role-based) → User                              │
│  Output: Rendered view for student/coach/admin                 │
└─────────────────────────────────────────────────────────────────┘
    ↓
HTTP Response
```

**Benefits:**
- ✅ Clear separation of concerns (5 layers)
- ✅ Each layer has single responsibility
- ✅ Easy to test (stateless, pure functions)
- ✅ Easy to extend (clear extension points)
- ✅ Easy to understand (linear flow)

## Component-Level Comparison

### Intent Classification

| Aspect | Current v2.1 | Proposed v3.0 |
|--------|-------------|---------------|
| **File** | `intentRouter.ts` (300+ lines) | `IntentRouter.ts` (50 lines) |
| **Responsibilities** | Intent + fact guardrails + routing | Intent classification ONLY |
| **Input** | Raw message string | `ParsedMessage` (structured) |
| **Output** | `{ shouldRoute: true, intent: 'gameplan' }` | `IntentCategory` enum |
| **Testability** | Hard (mixed concerns) | Easy (single responsibility) |

---

### Knowledge Retrieval

| Aspect | Current v2.1 | Proposed v3.0 |
|--------|-------------|---------------|
| **Files** | `resolverTools.ts` (105 functions) + scattered moat_* queries | `StudentFactsRetriever.ts` + `CoachingIntelligenceRetriever.ts` + `TemporalContextResolver.ts` |
| **Organization** | 105 separate functions (no cohesion) | 3 classes with clear interfaces |
| **Temporal Logic** | Scattered across 105 resolvers | Consolidated in `TemporalContextResolver` |
| **Coaching Intel** | Multiple tables (moat_tactic_chips, moat_essay_examples, etc.) | Single table `coaching_knowledge_base` |
| **Reusability** | Each agent calls different resolvers | All agents use same retrieval interface |

---

### Agent Orchestration

| Aspect | Current v2.1 | Proposed v3.0 |
|--------|-------------|---------------|
| **File** | `agentChat-utfa.ts` (500+ lines) | `AgentOrchestrator.ts` (100 lines) |
| **Responsibilities** | Session mgmt + dedup + agent selection + orchestration | Orchestration ONLY |
| **Agent Selection** | Hardcoded switch statement | `AgentSelector` class (extensible) |
| **Decision Making** | Mixed in BaseAgent.execute() | `DecisionMaker` class (testable) |
| **Clarity** | Hard to follow (mixed concerns) | Clear (separate components) |

---

### Response Composition

| Aspect | Current v2.1 | Proposed v3.0 |
|--------|-------------|---------------|
| **File** | `compose.ts` (200+ lines) | `ResponseExecutor.ts` (50 lines) |
| **Responsibilities** | Composition + meta-strip + humanization + storage | Execution ONLY (composition is in DecisionMaker) |
| **Humanization** | Inline logic | Separate method (easy to customize) |
| **State Updates** | Scattered across agents | Consolidated in `StateUpdater` |
| **Event Emission** | Manual in agents | Automatic via `EventEmitter` |

## Data Flow Comparison

### Current v2.1 Data Flow (Implicit)

```
User Message (string)
    ↓
intentRouter receives raw string
    ↓ (returns { shouldRoute, intent })
agentChat-utfa receives { shouldRoute, intent }
    ↓ (queries database inline)
    ↓ (selects agent via switch statement)
    ↓ (calls agent.execute() with minimal context)
BaseAgent receives minimal context
    ↓ (calls tools via manual loop)
    ↓ (tools query database directly)
    ↓ (returns raw LLM response)
compose receives raw LLM response
    ↓ (adds humanization)
    ↓ (stores to database inline)
    ↓ (returns final response)
Final Response (string)
```

**Problems:**
- ❌ Implicit data flow (no typed interfaces)
- ❌ Side effects everywhere (database queries inline)
- ❌ Hard to test (can't mock intermediate steps)
- ❌ Hard to debug (no visibility into intermediate state)

---

### Proposed v3.0 Data Flow (Explicit)

```
User Message (string)
    ↓
MessageParser.parse()
    ↓ ParsedMessage (structured)
StudentContextExtractor.extract()
    ↓ StudentContext (student position in journey)
SessionStateDetector.detect()
    ↓ SessionState (conversation state)
    ▼
PerceptionOutput = {
  parsed_message: ParsedMessage,
  student_context: StudentContext,
  session_state: SessionState
}
    ↓
StudentFactsRetriever.retrieve()
CoachingIntelligenceRetriever.retrieve()
TemporalContextResolver.resolve()
    ▼
KnowledgeOutput = {
  student_facts: StudentFacts,
  coaching_intelligence: CoachingIntelligence,
  temporal_context: TemporalContext
}
    ↓
IntentRouter.route()
    ↓ IntentCategory (enum)
AgentSelector.select()
    ↓ SpecialistAgent (customized for archetype)
DecisionMaker.decide()
    ▼
AgentDecision = {
  response_text: string,
  confidence: number,
  reasoning: string,
  sources: string[],
  next_actions: Action[]
}
    ↓
ResponseExecutor.execute()
StateUpdater.update()
EventEmitter.emit()
    ▼
ExecutionResult = {
  response: string,
  metadata: ExecutionMetadata
}
    ↓
ViewRenderer.render()
    ↓
Final Response (rendered view)
```

**Benefits:**
- ✅ Explicit data flow (typed interfaces at each step)
- ✅ No side effects (pure functions where possible)
- ✅ Easy to test (can mock each step)
- ✅ Easy to debug (can inspect intermediate state)

```typescript
// services/jenny-api/src/agents/NewAgent.ts

// Step 2: Register in AgentRegistry
// services/jenny-api/src/core/AgentRegistry.ts
agentRegistry.registerAgent('new_agent', new NewAgent(...));

// Step 3: Add intent routing
// services/jenny-api/src/router/intentRouter.ts
if (message.includes('new_keyword')) {
  return { shouldRoute: true, intent: 'new_agent' };
}

// Step 4: Add orchestration logic
// services/jenny-api/src/orchestrator/agentChat-utfa.ts
case 'new_agent':
  agent = agentRegistry.getAgent('new_agent');
  break;

// Step 5: Update compose.ts if needed
// Step 6: Update frontend routing if needed
// Step 7: Add new tools if needed
// Step 8: Update documentation

❌ 8+ files to modify, easy to forget steps
```

```typescript
    perception: PerceptionOutput,
```

## Monitoring & Observability Comparison

### Current v2.1: Basic Logging Only

```typescript
// services/jenny-api/src/orchestrator/agentChat-utfa.ts
logger.info('Agent chat started');
// ... lots of code ...
logger.info('Agent chat completed');

// ❌ Problems:
// - No metrics (latency, token usage, error rates)
// - No tracing (can't follow request across layers)
// - No alerts (can't detect issues proactively)
// - No dashboards (can't see system health)
```

---

### Proposed v3.0: Comprehensive Monitoring

```typescript
// services/agent-framework/src/cognition/DecisionMaker.ts
const startTime = Date.now();
const traceId = generateTraceId();

try {
  // Log start
  await this.monitoring.logEvent('decision_started', {
    trace_id: traceId,
    agent: agent.name,
    student_id: perception.student_context.student_id
  });

  // Make decision
  const decision = await agent.execute(perception, knowledge);

  // Record metrics
  const latency = Date.now() - startTime;
  await this.monitoring.recordMetric('decision_latency_ms', latency, {
    agent: agent.name
  });
  await this.monitoring.recordMetric('decision_tokens_used', decision.metadata.tokens_used);

  // Log success
  await this.monitoring.logEvent('decision_completed', {
    trace_id: traceId,
    latency_ms: latency,
    confidence: decision.confidence
  });

  return decision;

} catch (error) {
  // Record error
  await this.monitoring.recordMetric('decision_errors', 1, {
    agent: agent.name,
    error_type: error.name
  });

  // Trigger alert if error rate high
  await this.monitoring.triggerAlert({
    type: 'decision_error',
    severity: 'high',
    message: `Agent ${agent.name} failed: ${error.message}`
  });

  throw error;
}

// ✅ Benefits:
// - Metrics for every decision (latency, tokens, errors)
// - Tracing across all layers (can follow request)
// - Alerts for high error rates, slow responses
// - Dashboards showing agent performance
```

## Continuous Learning Comparison

### Current v2.1: Manual Extraction Only

```
1. Coach has successful session with student
2. Claude manually analyzes session transcript
3. Developer manually creates JSON file
4. Developer manually updates STUDENT_INDEX.md
5. (Intelligence NOT in database, NOT used by agents)

❌ Problems:
- Manual, time-consuming process
- Intelligence stays in JSON files (not accessible to agents)
- No validation (single student data, not validated across cohort)
- No feedback loop (can't learn from outcomes)
```

---

### Proposed v3.0: Automated Continuous Learning

```
1. Coach has successful session with student
    ↓
2. TrainingSystem.PatternExtractor automatically analyzes session
    ↓ (Extracts: frameworks, tactics, EQ patterns)
3. TrainingSystem.Validator validates across multiple students
    ↓ (Checks: Seen in 3+ students? Effective?)
4. TrainingSystem stores validated patterns in coaching_knowledge_base
    ↓
5. TrainingSystem.PlaybookUpdater updates agent playbooks
    ↓
6. Agents automatically use new patterns in next sessions
    ↓
7. EvaluationSystem tracks effectiveness
    ↓
8. TrainingSystem adjusts based on outcomes
    ↓
9. REPEAT (continuous improvement)

✅ Benefits:
- Fully automated (no manual extraction)
- Intelligence in database (immediately accessible)
- Validated across students (only keep what works)
- Feedback loop (learn from outcomes)
- Continuous improvement (system gets better over time)
```
