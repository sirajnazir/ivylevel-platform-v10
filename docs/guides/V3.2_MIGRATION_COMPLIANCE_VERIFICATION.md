### 3. mv_hgti_scores Materialized View (COMPLIANT ✅)

**v3.2 Production Schema (Actual):**
```sql
CREATE MATERIALIZED VIEW mv_hgti_scores AS
SELECT
  student_id,
  AVG(transformation_delta) AS avg_transformation,
  SUM(CASE WHEN breakthrough THEN 1 ELSE 0 END) AS breakthrough_count,
  COUNT(*) AS total_events,
  MAX(occurred_at) AS latest_event_date
FROM growth_events
GROUP BY student_id;

CREATE UNIQUE INDEX ON mv_hgti_scores(student_id);
```

**Migration Plan Refresh (Proposed):**

**Compliance Check:**
- ✅ View definition matches migration expectations

## ✅ Risk Assessment

### Migration Risks (All Mitigated ✅)

#### Risk 1: Schema Incompatibility
**Risk:** Migration scripts insert data that doesn't match v3.2 schema
**Mitigation:** ✅ Schema verified 100% compliant (see sections above)
**Status:** LOW RISK

#### Risk 2: Data Loss
**Risk:** Migration overwrites or deletes existing data
**Mitigation:**
- ✅ Migration uses INSERT only (no UPDATE/DELETE)
- ✅ ON CONFLICT DO NOTHING (prevents duplicates)
- ✅ Source data preserved in v14 tables (read-only)
- ✅ Backup recommended before migration
**Status:** LOW RISK

#### Risk 3: Duplicate Data
**Risk:** Migration creates duplicate chips/events
**Mitigation:**
- ✅ Unique constraint on chips(student_id, hash)
- ✅ Hash computed from content (deduplication)
- ✅ Scripts use ON CONFLICT DO NOTHING
**Status:** LOW RISK

#### Risk 4: Performance Impact
**Risk:** Migration degrades production performance
**Mitigation:**
- ✅ Migration runs offline (before production deployment)
- ✅ Materialized view refresh is non-blocking
- ✅ Indexes already created on chips/growth_events tables
- ✅ Expected data volume: 200-250 total records (tiny)
**Status:** LOW RISK

#### Risk 5: API/UI Breaking Changes
**Risk:** Migrated data format breaks existing APIs/UI
**Mitigation:**
- ✅ APIs already tested with v3.2 chip format
- ✅ UI already tested with v3.2 chip format
- ✅ Migration uses same format as test data (proven working)
**Status:** LOW RISK
